# ADR-0017: HRM payslip engine — computation over record-keeping, attendance-gated

**Date:** 2026-07-07
**Status:** Accepted
**Deciders:** Mridha

---

## Context

There are two fundamentally different ways to approach payslips in a business SaaS:

1. **Record-keeping**: HR generates payslips in an external payroll tool (Excel, Tally, a
   government system) and uploads PDFs. The application is a filing cabinet — it stores and
   shows payslips but does not compute them.

2. **Computation engine**: The application computes each payslip from first principles — salary
   components, attendance data, leave records, and formula expressions. HR configures the rules;
   the system produces the numbers.

A computation engine is significantly more complex to build but is the correct choice for
a product that targets medium-sized companies operating across multiple countries.

A secondary question: in what order must data be ready before a payslip can be generated?

---

## Decision

**Build a computation engine, not a record-keeper.** Payslips are generated by a `PayrollRun`
that evaluates each employee's active salary structure against their attendance period data.

**Attendance period must be finalized before a payroll run can be created.** This is enforced
as a service-layer precondition, not a suggestion.

**Payslips are immutable once a payroll run is finalized.** If there is an error, HR creates a
correction component in the next period — payslips are never edited after locking.

---

## Reasoning

### Computation over record-keeping

The product vision is a unified Business Operating System that competes with HibBob, BambooHR,
and ultimately Workday. None of these products ask HR to upload PDFs. The payroll computation
capability is the product differentiator.

More concretely: a record-keeping approach makes it impossible to answer these questions
from within the application:
- "What was the total payroll cost for the Engineering department in Q2?"
- "How much overtime pay did we disburse last month?"
- "Which employees are at risk of LOP deduction because of attendance gaps?"

Computation produces structured `PayslipLine` records per component, making these questions
straightforward SQL aggregates.

### Country-agnostic by design

The requirement was explicitly not Bangladesh-specific. No hardcoded tax rules, no hardcoded
PF/ESI calculations, no hardcoded currency. Every rule is a salary component with a formula
or slab configuration that HR defines (see ADR-0015). The system ships with no pre-configured
components. The first HR admin for any organisation configures their own rules from scratch.

This is more setup work for the first admin, but it is the only architecture that works across
countries without maintaining a "country plugin" system.

### Attendance period must be finalized first

The payslip formula environment includes `WORKING_DAYS`, `ACTUAL_DAYS`, `ABSENT_DAYS`, and
`OVERTIME_HOURS`. These values come from the `AttendancePeriod` aggregate for the relevant
month. An open attendance period (still accepting punches and corrections) produces incorrect
values.

The precondition is enforced in `payroll.Service.CreateRun()`:

```go
period, err := s.attendanceRepo.FindPeriod(ctx, orgID, year, month)
if period == nil || period.Status != "finalized" {
    return nil, ErrAttendancePeriodNotFinalized
}
```

This is not a soft warning — it is a hard rejection. HR must close the attendance period
first. This prevents the most common payroll error: generating payslips before attendance
corrections are complete, then having to void and regenerate everything.

### Payslip immutability

A payslip is a financial record. Once an employee has been paid based on it, changing the
numbers retroactively is both technically incorrect and legally problematic in most jurisdictions.

The correct pattern — used by all serious payroll software — is a correction in the next period:
an additional `PayslipLine` with `is_one_time: true`, `component_type: earning` or `deduction`,
and a `note` explaining what it corrects. This approach:
- Maintains a complete audit trail
- Does not break accounting reconciliations for the prior period
- Is how accountants already think about payroll corrections

The `payslip.is_locked` field is set to `true` when `payroll_run.status = finalized`. Any
attempt to update a PayslipLine on a locked payslip returns `ErrPayslipLocked`.

### Payslip dispute via acknowledgement decline

Employees acknowledge payslips via the C4 AcknowledgementRecord mechanism. If an employee
believes their payslip is incorrect, they decline to acknowledge it and provide a reason.
This creates a record without creating a separate "dispute" object.

A separate `PayslipDispute` model was considered and rejected: it adds schema complexity and
a new status machine for a flow that is adequately handled by `acknowledgement.status = declined`
plus a free-text reason. HR sees declined acknowledgements in the payroll dashboard and can
create a correction component for the next run.

### Payslip computation flow (per employee per run)

```
1. Fetch active EmployeeSalaryRecord (effective_date ≤ period)
2. Fetch SalaryStructure + ordered components
3. Fetch attendance summary from finalized AttendancePeriod
4. Build formula env: {BASIC, GROSS=0, WORKING_DAYS, ACTUAL_DAYS, ABSENT_DAYS, ...}
5. For each component in display_order:
   a. Evaluate: fixed / pct / formula / slab / manual
   b. If type = earning: GROSS += result
   c. Create PayslipLine with formula_expression snapshot
6. Compute totals: gross_earnings, total_deductions, employer_contributions, net_pay
7. Create Payslip with status = draft
8. If pro-rata needed (joiner mid-period): service detects effective_date > period_start
   and wraps each component value in (ACTUAL_DAYS / WORKING_DAYS) factor automatically
```

PayslipLine snapshots the `formula_expression` and `calculation_method` at computation time.
If a component formula is later changed, historical payslips remain accurate.

## Alternatives considered

| Option | Reason rejected |
|--------|----------------|
| Record-keeping (PDF upload only) | Cannot produce structured data for reporting; does not compete with market-rate HRIS products; requires external payroll tool dependency |
| Allow payslip run before attendance finalization | Produces incorrect `ABSENT_DAYS` and `OVERTIME_HOURS`; requires voiding and regenerating when corrections come in; the friction of requiring finalization is intentional |
| Allow payslip editing after finalization | Creates an audit trail gap; breaks accounting reconciliation; not how any real payroll system works |
| Separate dispute record (PayslipDispute model) | Over-engineering for a flow that is fully handled by acknowledgement decline + note |
| Country-specific tax calculation built-in | Impossible to maintain for all target markets; locks out non-BD customers; the formula engine (ADR-0015) makes this unnecessary |

---

## Consequences

**Positive:**
- Payslip data is structured — every component is a row in `payslip_lines`; SQL aggregations
  for reporting work without parsing PDFs
- Formula snapshots mean historical payslips are always reproducible and auditable
- The attendance finalization gate prevents the most common class of payroll errors
- Pro-rata for mid-period joiners is handled automatically via formula variables, not a
  separate code path

**Negative:**
- Significantly more complex to build than a PDF upload system — requires Group A (salary
  config), Group D1 (attendance), and the formula engine all to be working first
- HR must finalize attendance before running payroll — this is a workflow change for any
  organisation that previously processed payroll and attendance in parallel
- Initial setup (configuring all salary components and structures) requires HR admin time;
  there is no out-of-the-box template for any country
